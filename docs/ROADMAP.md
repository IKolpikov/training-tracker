## Что уже работает (на 2026-05-28)

**Стек:** React+Vite+Tailwind на Vercel · Google Apps Script Web App (`backend/Code.gs`) →
Google Sheet (один файл `1t_YwN…`).

**Источник истины — Google Sheet** (тренер/пользователь редактирует, приложение читает):
- `Week Plan May 2026` — силовой/cardio план (Day, Type, Name, Sets, Reps, Unit, Load, Load unit, Notes)
- `Habbits` — привычки по дням (День, Рутина)
- `Польза` — бэклог разовых задач
- `Total load plan May 2026` — справочная сводка (НЕ читается приложением)
- `Log` — единый append-only журнал всех событий

**Backend `/exec` actions:** `logs` (GET, ?week=), `plan`/`habits`/`polza` (GET, конфиг),
`doPost` append (лог-строка) и `{action:"delete", timestamp}` (удаление).
ID выводится: явная колонка `id` → канон-карта по имени → slug (Cyrillic→Latin).

**Ключевые инварианты, выстраданные кровью:**
- Один Log, append-only. Удаление = delete по timestamp. НЕ заводить второй лог.
- `timestamp` — мс-точность, уникален per-set. Колонки timestamp/date/L/M/N пишутся как
  ПЛОСКИЙ ТЕКСТ (`setNumberFormat("@")`) — иначе Sheets парсит в Date/число и сдвигает tz /
  схлопывает trailing-zero секунды.
- `VITE_API_URL` живёт в Vercel env (НЕ в репо). Без него фронт молча падает в fallback.
- Любое действие пользователя → на бэк (append И delete). Состояние нигде не живёт только
  локально; localStorage = кэш + офлайн-очередь.
- carry-математика (`progress.js`): дефицит/профицит едет на ближайший следующий **scheduled**
  день; сегодня/будущее не двоится; считается только по закрытым (до 04:00) дням.
- ⟳ перечитывает ВСЁ: logs недели + Польза + конфиг. Зелёная/красная точка = реальный статус.
- Польза done-state = из логов на сервере (кросс-устройство), НЕ localStorage.

**Тесты (гонять перед «готово»):** `npm test` (Vitest, математика+парсинг), `npm run test:backend`
(живой /exec: round-trip, delete, no-dup). Build id виден в углу шапки.

## Цель развития: тренер ⇄ атлет через таблицу

Тренер пишет план построчно в Google Sheet → появляется в приложении → атлет выполняет и
логирует → тренер читает логи построчно, сверяет план vs факт → ставит новый план на неделю.

Принцип: и план, и лог — **строчно-структурированы** (одна строка = один атом). Никакого
парсинга свободного текста.

## Беговые / вело тренировки (RUN / CYCLE) — спроектировано, не построено

Беговой/вело план = **последовательность РАЗНЫХ сегментов** (не N одинаковых сетов).
Отдых — это ТОЖЕ сегмент (часто бег с заданием: 200м трусцой / 1 мин @ HR≥150).

**Решения (зафиксированы с пользователем):**
- Единый Log, без раздельного журнала.
- Новые типы `RUN` и `CYCLE`. CYCLE структурно = RUN; отличие — отображение
  (бег — темп мин/км; вело — скорость км/ч). `Z2 long cycling` = CYCLE с 1 сегментом.
- **Явная колонка `type` в Log**: `STR / ISO / CARDIO / RUN / CYCLE / HABIT / POLZA`.
- distance / time / pace — **связанная тройка «любые два → третий считается»**:
  · distance+time → pace (обычно) · time+pace → distance («12 мин по 4:15») · distance+pace → time.
  Все три редактируемы; заполнил два — третье подставилось; правишь поле — пересчитывается
  НЕ-тронутое. Pace идёт последним полем (чаще всего именно он вычисляется). Сохраняем все три
  как снимок (консистентны на момент сохранения; тренер читает pace напрямую).
  Формула: pace(сек/км) = time_сек / (distance_м / 1000).

**Лист `Running Plan` — одна строка = один сегмент (rest_sec ВЫКИНУТ, отдых = сегмент):**
```
Day | block | seq | kind | label | distance_m | target_pace | target_time | target_hr | notes
Сб  | intervals | 1 | wu       | разминка | 1500 | 6:30 |      | 130 |
Сб  | intervals | 2 | interval | 800 #1   | 800  | 3:45 | 3:00 | 175 |
Сб  | intervals | 3 | rest     | трусца   | 200  | 6:00 |      | 150 | не ниже 150
Сб  | intervals | 4 | interval | 800 #2   | 800  | 3:45 | 3:00 | 175 |
…
```
- `kind` ∈ `interval` / `rest` / `wu` / `cd`. Время/темп в формате m:ss.

**Счётчик карточки** считает ТОЛЬКО `kind=interval`. Отдых/wu/cd логируются, но в `[done/target]`
не входят. Пример: 2 интервала + отдых между ними → карточка `2/2`, в модалке **3 блока**
(оба интервала + отдых, у отдыха тоже вносится факт).

**Поля факта на сегмент (дефолты из плана, каждое правится), в порядке:**
Дистанция (м) · Время (m:ss) · Пульс средний · Пульс макс · Скорость (мин/км, обычно
вычисляется — стоит последней).

**Парсер времени/темпа** — одна функция на оба поля. Съедает `03:14`, `3:14`, `3.14`, `3'14`,
`3 14` → канон `m:ss`. Хранится текстом ТОЧНО (без округления / потери секунд). Минуты без
ведущего нуля ок.

**Log: новые колонки** `type`, `hr_avg`, `hr_max`, `seq` (+ distance/time/pace в L/M/N).

**Темповые** — частный случай RUN (wu + tempo + cd), та же модель.

### Фазы
1. ✅ Кнопка модалки → «Done»
2. Малый шаг: пульс (avg/max) в cardio-логировании + показ вычисленного темпа
3. Основное: лист `Running Plan` + типы `RUN`/`CYCLE` + рендер сегментов (вкл. rest) +
   лог по сегменту + колонки `type`/`hr_avg`/`hr_max`/`seq` в Log + парсер времени/темпа
   (один редеплой Code.gs на всё)
4. Темповые переводим на ту же модель

### Чего НЕ делать
- Не плодить второй лог · не парсить план из свободного текста · не округлять секунды

## Фаза 5: ингест из Garmin/Strava (Claude-скилл, schema-first) — спроектировано

Цель: не впечатывать HR/время руками. Сырьё активности → наша сегментная схема → POST в `/exec`.

**Архитектура — два слоя, склеенные схемой Log:**
- Слой 1 (React-приложение): ручной ввод + отображение + Log как источник истины.
  НЕ тащить сюда FIT-парсинг и Strava OAuth (тяжело, хрупко, OAuth на статике требует бэкенда).
- Слой 2 (ингест — отдельный Claude-скилл): TCX → выравнивание по плану → POST строк в тот же
  `/exec`. Приложение показывает их как залогированное.
- Мост: **схема сегмента Log** (type/seq/distance/time/pace/hr_avg/hr_max). Проектируется в
  фазе 3; и ручной ввод, и импортер пишут ОДИНАКОВЫЕ строки. Импортер = ещё один писатель.

**Почему Claude, а не парсер:** свёртка шумных лапов в сегменты плана — judgment-задача
(пропущенные лапы, GPS-дрейф, дробление). LLM с контекстом плана раскладывает, жёсткий код ломается.

**Формат:** TCX (XML; есть у Garmin Connect и Strava Export; содержит per-lap avg/max HR +
потрекпойнтовый HR/дистанцию/время). FIT — бинарь (сложнее). GPX — без HR. → берём TCX.

**Реальное поведение лапов (пример «2×800»):**
home→стадион (1 лап, медленно) · разминка (пара лапов) · [пауза] · 4×200 быстро · отдых (1 лап) ·
4×200 быстро · заминка домой. Лапы НЕ 1:1 с сегментами: интервал 800м = 4×200м-лапа.
«Новая активность vs один заход» — оба ок (один заход режется по темпу).

**Алгоритм свёртки (импортер):**
1. Все лапы: distance/time/pace/HR + паузы.
2. Темп — главный сигнал: быстрые кластеры (~target pace) = работа, медленные = WU/CD/rest.
3. План — шаблон: знает «2 интервала по 800» → группирует подряд быстрые 200м-лапы в ~800м.
4. Медленное до 1-го быстрого = WU, между = rest, после = CD.
5. Агрегат на сегмент: Σdistance, Σtime, pace из них, HR avg (взвеш. по времени), HR max (макс по группе).

**Гранулярность:** основной Log = на уровне сегмента плана (800м: план vs факт — для тренера).
200м-сплиты импортер кладёт в `notes` сегмента строкой (напр. `splits: 56/57/58/61s`) — глазами
видно раскладку, структуру не раздуваем.

**Авто-Strava (без ручного экспорта)** — позже: OAuth-приложение + refresh-токены (Apps Script
OAuth2-библиотека). Инфраструктура — только после обкатки ручного TCX-потока.

**Порядок:** сначала фаза 3 (ручной RUN/CYCLE фиксирует схему) → потом импортер льёт в неё.
