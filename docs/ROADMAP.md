## Что уже работает (на 2026-05-28)

**Стек:** React+Vite+Tailwind на Vercel · Google Apps Script Web App (`backend/Code.gs`) →
Google Sheet (один файл `1t_YwN…`).

**Источник истины — Google Sheet** (тренер/пользователь редактирует, приложение читает):
- `Week Plan May 2026` — силовой/cardio план (Day, Type, Name, Sets, Reps, Unit, Load, Load unit, Notes)
- `Habbits` — привычки по дням (День, Рутина)
- `Польза` — бэклог разовых задач
- `Total load plan May 2026` — справочная сводка (НЕ читается приложением)
- `Log` — единый append-only журнал всех событий

**Backend `/exec` actions:** `logs` (GET, ?week=), `plan`/`habits`/`polza` (GET, конфиг),
`doPost` append (лог-строка) и `{action:"delete", timestamp}` (удаление).
ID выводится: явная колонка `id` → канон-карта по имени → slug (Cyrillic→Latin).

**Ключевые инварианты, выстраданные кровью:**
- Один Log, append-only. Удаление = delete по timestamp. НЕ заводить второй лог.
- `timestamp` — мс-точность, уникален per-set. Колонки timestamp/date/L/M/N пишутся как
  ПЛОСКИЙ ТЕКСТ (`setNumberFormat("@")`) — иначе Sheets парсит в Date/число и сдвигает tz /
  схлопывает trailing-zero секунды.
- `VITE_API_URL` живёт в Vercel env (НЕ в репо). Без него фронт молча падает в fallback.
- Любое действие пользователя → на бэк (append И delete). Состояние нигде не живёт только
  локально; localStorage = кэш + офлайн-очередь.
- carry-математика (`progress.js`): дефицит/профицит едет на ближайший следующий **scheduled**
  день; сегодня/будущее не двоится; считается только по закрытым (до 04:00) дням.
- ⟳ перечитывает ВСЁ: logs недели + Польза + конфиг. Зелёная/красная точка = реальный статус.
- Польза done-state = из логов на сервере (кросс-устройство), НЕ localStorage.

**Тесты (гонять перед «готово»):** `npm test` (Vitest, математика+парсинг), `npm run test:backend`
(живой /exec: round-trip, delete, no-dup). Build id виден в углу шапки.

## Цель развития: тренер ⇄ атлет через таблицу

Тренер пишет план построчно в Google Sheet → появляется в приложении → атлет выполняет и
логирует → тренер читает логи построчно, сверяет план vs факт → ставит новый план на неделю.

Принцип: и план, и лог — **строчно-структурированы** (одна строка = один атом). Никакого
парсинга свободного текста.

## Беговые / вело тренировки (RUN / CYCLE) — спроектировано, не построено

Беговой/вело план = **последовательность РАЗНЫХ сегментов** (не N одинаковых сетов):
WU 1.5км @6:30 · 800м @3:45 ×6 (отдых 60с) · CD 1км. Нужна структура «план = список сегментов».

**Решения (зафиксированы с пользователем):**
- Единый Log, без раздельного журнала.
- Новые типы `RUN` и `CYCLE`. CYCLE структурно = RUN; разница только в отображении
  (бег — темп мин/км, вело — скорость км/ч). `Z2 long cycling` = CYCLE с 1 сегментом.
- **Явная колонка `type` в Log**: `STR / ISO / CARDIO / RUN / CYCLE / HABIT / POLZA`
  (раньше тип выводился из префикса id; явная колонка упрощает фильтрацию тренеру).
- Скорость/темп = производная (distance/time). НЕ храним, выводим на лету (в таблице — формулой).

**Новый лист `Running Plan` — одна строка = один сегмент:**
```
Day | block | seq | label | distance_m | target_pace | rest_sec | notes
Сб  | intervals | 1 | WU     | 1500 | 6:30 | 0  | разминка
Сб  | intervals | 2 | 800 #1 | 800  | 3:45 | 60 |
…
```
(время/темп в формате m.ss, напр. 3.45 = 3 мин 45 сек)

**Рендер:** карточка RUN/CYCLE раскрывается в список сегментов. План (distance + target_pace) —
read-only описание. Лог по сегменту: фактическое время + пульс. Скорость считается, показывается.

**Log: новые колонки** `hr` (пульс), `seq` (номер сегмента). distance/time уже есть (L/M/N).

**Темповые** — частный случай RUN (WU + темп + CD), та же модель.

### Фазы
1. ✅ Кнопка модалки → «Done»
2. Малый шаг: поле «пульс» (hr) в cardio-логировании + показ вычисленного темпа/скорости
3. Основное: лист `Running Plan` + типы `RUN`/`CYCLE` + рендер сегментов + лог по сегменту +
   колонки `type`/`hr`/`seq` в Log (один редеплой Code.gs на всё)
4. Темповые переводим на ту же модель

### Чего НЕ делать
- Не хранить вычисляемую скорость · не плодить второй лог · не парсить план из свободного текста
